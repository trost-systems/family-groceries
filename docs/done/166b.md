# Job 166b: the network watch's two edge cases

Follow-up to job 166 (review.0, nice to have 1 to 3).

- **Stale first check.** `app/lib/app/network.dart` drops the start-up check's answer once the
  plugin has reported a change, so an older `up` can no longer undo a real `down`.
- **Dead socket after a drop.** After a real down and up, `ListCubit._reconnect` asks
  `ListRepository.renewRealtime` to close the realtime socket if the list's channel still says
  up. The client opens a new socket and every channel joins again. A plain channel rewatch (the
  brief's idea) was measured and rejected: it goes over the same dead socket (DECISIONS, "Job
  166b").
- **Measured on the web build** with every frame of the old socket swallowed: a partner's add
  showed 39.5 s after it was made on job 166, 0.16 to 0.81 s with the fix (5 runs, dead and
  live socket). „Offline“ clears about 2.9 s after the network returns (was 1.8 s).
- **Suspect from the down.** The channel stops counting as up when the OS says down, so a
  retry that answers while the network settles cannot clear „Offline“ before the renewal.
- **Tests.** `app/test/app/network_test.dart` "a change before the first check answers beats
  that answer"; `app/test/list/list_cubit_test.dart` "after a real down, a channel that still
  says up is not trusted ..." (both failed first, commit "Failing tests"); e2e
  `connectivity.spec.ts` "a realtime socket that died with the network is replaced ..." (6/6
  locally with the fix; 2/2 failed on job 166's code at the add). verify.sh gitleaks, lint and
  flutter passed.
