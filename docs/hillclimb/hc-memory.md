# hc-memory hill climb (job 107)

Started: 2026-11-05 07:09:33 CET
Start epoch: 1793858973

## Goal

Lower the Flutter app's memory on the Linux desktop build (profile mode) under Xvfb across a fixed
scripted session against the local Supabase stack. Lower is better.

**Score** = 0.5 × peak RSS (MB) + 0.5 × steady-state RSS (MB).

- Peak RSS is the kernel's high-water mark `VmHWM` of the app process at the end of the session
  (exact, so it does not depend on when a sample happens to land). The sampled peak is reported next
  to it as `peakRssSampledMb`.
- Steady-state RSS is the median `VmRSS` over the last 30 s of a 60 s idle on the list.

## Harness

`tool/hillclimb/hc-memory/measure.sh` (run from anywhere in the checkout, needs the checkout's local
stack running) prints one JSON line. It:

1. Builds `app/test_driver/main_hc_memory.dart` with `flutter build linux --profile` (in the
   `linux-build` container of the verify-family-groceries skill, since the host has no CMake). The
   entrypoint is the Marionette app plus one service extension, `ext.hc.imageCache`, that reports the
   image cache (profile builds cannot evaluate expressions).
2. Seeds `tool/hillclimb/hc-memory/hc-memory-300.yaml` with `fg seed` (the job 18 fixtures) as run
   `hc-memory`: one user, one household, three stores, 300 open items. The YAML is generated by
   `gen-scenario.mjs` with seed 107 and committed. It turns the local `premium_offer` switch on so
   Mehr lists Hummlist Premium (local database only).
3. Under `flock /tmp/fg-hc-measure.lock`, runs `session.mjs` in `xvfb-run -a` (screen 412×892, the
   runner's default window). `session.mjs` starts the bundle with fresh XDG dirs, connects to the
   VM service and drives the app through Marionette's service extensions:
   sign in through the login screen; open the list (dismiss the hint card if shown); scroll top to
   bottom and back 3× (45 drags of 500 px each way, so each pass reaches the end); add 20 fixed new
   items through the add bar (Enter takes the first suggestion, waits for the added note); tick those
   20 (scrollTo, drag clear of the header, tap, wait until the row leaves); open and close the add
   sheet; Mehr; Hummlist Premium (waits for the yearly price card), back; Liste; idle 60 s.
   Every 250 ms it samples `VmRSS` from `/proc/<pid>/status` and `getMemoryUsage` (Dart heap) from
   the VM service, tagged with the phase.
4. Checks the work happened: the household must end with 300 active and 20 bought items (300 seeded
   + 20 added − 20 ticked), else the run fails and names the added item left active. Then it tears
   the run down.

`parts` carries the peak, steady, Dart heap (steady and peak), image cache, per-phase RSS and Dart
heap maxima, the sample count, the Marionette action count, the sample error count and the session
length.

Why it is deterministic: fixed data (seeded YAML), fixed window, fixed action script with no
randomness (the only seed, 107, is the generator's), drags without timestamps (no fling, so each
drag scrolls exactly its distance), waits on UI state instead of wall-clock where the script depends
on it, and a work check. What is not fixed: the host is shared (load 10-14 on 12 cores), GC timing
and the software GL driver (Mesa llvmpipe under Xvfb) vary with it.

The parts are those of each side's median run. The final runs (2026-11-05 13:50-14:03 CET)
are of the branch rebased on main (`1ba6dc51`), interleaved with two runs of main's own runner
on the same tree (trim, main, trim, main, trim). Those scored 413.9 and 411.0, so the
baseline still holds after the rebase and the harness clean-up, and the step is worth about
−31 against them. Every run passed the work check (300 open, 20 bought).

**Launch RSS is one sample and is not compared.** The `launch` phase holds the single sample
taken when Marionette has registered, while the engine is still starting, so it moves with
timing: 265-278 MB in the baseline runs, 280-296 MB in trim runs under Impeller, 238-240 MB in
the Skia runs. The earlier "launch 290 → 240" in row 5 compared one trim run with one Skia run;
the old result table compared a different pair. Neither is a measurement of a step, so the
launch row is out of the table.

Kept:

1. **Attempt 2.** The Linux runner calls `malloc_trim(0)` every 5 s from the GTK main loop
   (`app/linux/runner/my_application.cc`). glibc kept the pages that the engine, Impeller and the
   GL driver had freed. Final tree: 381.0 against 413.7.

**What one trim costs.** A temporary build (not committed) timed every `malloc_trim(0)` call
during a full session: 33 calls, median 0.82 ms, p90 1.56 ms, max 2.2 ms, on the GTK main
thread every 5 s. glibc holds each arena's lock while it trims, so a thread that allocates in
that window waits up to about 2 ms; one 60 Hz frame is 16.7 ms. Frame times were not measured.
That build also had the Skia switch; it scored 329.2.

**Removed by the lead (addendum 3): attempt 5, Skia instead of Impeller.** It lowered the score
by about 43, but no CI job builds `app/linux`, so nothing but single harness runs and three
screenshot pairs backed switching the verification surface's renderer. The shipped iOS and
Android apps render with Impeller, so the surface stays on Impeller too. The screenshot pairs
stay in `docs/screenshots/107/` as the evidence for that attempt;
`tool/hillclimb/hc-memory/pixel-diff.py` recomputes their numbers (3.74 %, 3.83 %, 8.15 % of
pixels differ, max 112, 86, 141 of 255).

**Reverted after review 0: attempt 6** (a 4 MB Skia GPU resource cache, `lib/main.dart`). Its
first measurement compared a median of 3 against one run of the previous step; A/B pairs on one
tree showed no difference (log row 6).

What did not move the score (each inside the band): glibc arena count (twice), a fixed mmap
threshold (twice), trimming every second, a 4 MB and a 1 MB Skia cache, running the UI isolate
on the platform thread, and folding `ListState.items` once per state. The Dart heap is small
here: after a full GC at idle 21.5 MB is in use, most of it program metadata (code, functions,
classes); the app's own data is a few MB. Most RSS is native: at idle under Impeller with the
trim, anonymous 119 MB, `[heap]` 69 MB, `libLLVM` 62 MB (llvmpipe), Dart heap mapping 50 MB.

**Who gains.** Only the Linux build: the verify-family-groceries surface and this harness. No
shipped app (iOS, Android, web) runs the Linux runner, so the gain is for tooling, not users.

**Harness changes after the baseline (review 1, no effect on what is measured):** `measure.sh`
now reads the local `premium_offer` switch first and puts it back, and tears the run down, in an
EXIT trap (before, the switch stayed on). `session.mjs` lost its debug branches
(`HC_DEBUG_TICK`, `HC_SCROLL_DUMP`) and a no-op JSON round trip. The measured path is the same;
the interleaved main-runner runs above (413.9, 411.0) match the baseline (413.7).

### Next, if pushed further

- Measure with Skia on a desktop with a GPU, and build `app/linux` in CI, before deciding the
  renderer of the verification surface again.
- The idle allocation profile holds about 1,500 `SemanticsConfiguration` objects: semantics is on
  in this build. If the GTK embedder mirrors each node natively (a guess, not checked), a smaller
  semantics tree on the list would shrink the main arena. That changes what screen readers get,
  so it needs a design pass, not a hill-climb step.
- `DeviceCache`: the list snapshot shares the shared-preferences file with every other key, so
  each save re-encodes the whole file. Its own file would cut the Dart churn per tick (not a
  measurable RSS change at this band).
