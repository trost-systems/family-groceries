# Households wave 3: club features

Job 169b, wave 3 of 3. Builds on waves 1 and 2 ([`W1.md`](W1.md), [`W2.md`](W2.md)). Design
source: [`PLAN.md`](PLAN.md) section 6, parts K, L and M. Peter (2026-11-08, Q-HH5): club features
stay in the build; no club outreach, no club research, no club landing page (part N is out).

## K. Several lists per household

A club runs a "Sommerfest" list next to a "Vereinsheim" list; a family keeps "Wocheneinkauf" and
"Baumarkt". Stores, categories, their order and the classifier stay per household.

Data:

- `lists (id, household_id, name 1-60, position, created_at, created_by)`, RLS
  `is_household_member(household_id)`, two-household case in `rls.test.sql`, in the realtime
  publication.
- Every household has at least one list. The migration creates "Einkaufsliste" for every
  household; `create_household` creates it with the household. The last list can't be deleted.
  That first list carries `seed_key = 'main'`: the app shows it in the UI language ("Shopping
  list") while its name is the seeded one, like seeded categories. MCP and the API keep the
  stored name.
- `items.list_id uuid not null`, foreign key `(list_id, household_id)` to `lists (id,
  household_id)` with `on delete cascade`. A before-insert trigger fills a missing `list_id` with
  the household's first list (by `position`, then `created_at`): old store builds, Siri, Alexa
  and API calls without a list keep working and land in the first list.
- The open-item duplicate rule (job 64) becomes per list: the same name may be open on two
  lists.
- `item_events` keep the item's `list_id` for history.

RPCs: `create_list(p_household, p_name, p_id)` (client id, idempotent), `rename_list(p_list,
p_name)`, `delete_list(p_list)` (`last_list` when it is the only one; its items go with it),
`move_list(p_list, p_position)`. Any member may manage lists (as with stores today).

Integrations: MCP list tools gain an optional `list` argument (id or exact name) next to
`household`, plus `list_lists`; without `list`, `tick_items` and `move_item` find an item given
by its id on any list of the household (a name means the first list); the public API gains `list_id` on items and `GET /v1/lists`
(contract in `docs/api/openapi.yaml`); Siri, Alexa and voice write to the first list of the
default household (unchanged answers).

Old store builds see every list's items as one list (they don't know `list_id`); their writes go
to the first list. Accepted for the transition; the household page says nothing about it.

App:

- The list screen shows the household chip (W1) and, when a household has two or more lists, a
  row of list tabs under the header (horizontal scroll, the shown list highlighted, a "+" at the
  end). With one list: no tabs, and "Neue Liste" lives in the household page.
- Items carry `list_id`; `AddItem` sends the shown list; a new `ItemOp` variant `MoveToList`
  moves an item to another list (edit sheet "Liste" picker). The device copy (items, write
  queue, claims) stays one per user and household; the shown list is remembered per user and
  household. Realtime stays per household and the cubit filters by list. A list's delete event
  can't be filtered by household and names only the list's id: the app reloads its lists only
  when the id is one of its household's.
- Lists are managed in the household page ("Listen": rename, reorder, delete with confirm).

## L. "Ich bringe" claims

For a club party or a family gathering: members say what they bring.

- `item_claims (id, item_id, household_id, user_id, quantity text null, created_at)`, a random
  `id` as primary key and `unique (item_id, user_id)`, RLS `is_household_member(household_id)`,
  realtime, rls case. Realtime sends a delete's primary key to every subscriber of the table,
  without RLS or filters, so the key must not name the claimant; the app drops a deleted claim by
  its id. `rls.test.sql` checks that no published table's key references a user.
- RPCs: `claim_item(p_item, p_quantity)` (upsert, idempotent), `unclaim_item(p_item)`.
  A claim ends when the item is ticked, deleted or the claimant leaves (cascade / trigger).
- App: the edit sheet gets "Ich bringe das" (optional amount, e.g. "2 Kuchen"); the row shows
  "Mia bringt" / "Mia bringt 2 · Tom bringt 1" under the name; a claim on your own row shows
  "Du bringst". New `ItemOp` variants `ClaimItem` / `UnclaimItem` (idempotent, optimistic, like
  every item write).
- MCP: `claim_item` is not exposed (claims are a person's promise, not an agent's).

## M. Join approval

- `households.join_approval boolean not null default false`, set by owner/admins on the
  household page ("Beitritte bestätigen"). Default on for `kind = 'club'` households created
  after this wave; off for all others.
- With approval on, accepting any invite creates a `join_requests (id, household_id, user_id,
  invite_id, created_at, decided_at, decision)` row instead of a membership and answers
  `{status: 'requested', household_id}`. RLS: admins/owner of the household and the requester
  see it.
- RPCs: `household_join_requests(p_household)` (admins), `decide_join_request(p_request,
  p_approve)` (admins; approve inserts the membership and an `invite_uses` row and counts the use),
  `cancel_join_request(p_request)` (requester), `my_join_requests()`.
- An approval whose invite has no use left answers `invite_full` and leaves the request open;
  the household page says so under the request and asks for a new link. The requester opening a
  new link of the household moves the open request to that invite, so the next approval counts
  there.
- A declined user can't ask the same household again for 24 hours: `accept_invite` answers
  `declined_recently` (no household id, so the oldest builds' `join_household` answers null) and
  files nothing; the join screen says so plainly, not as an error.
- `household_join_requests` leaves out a request from someone who is a member by now (they joined
  through a link while approval was off); deciding such a request closes it as `cancelled`.
- The joiner sees "Anfrage gesendet: ein Admin von „X" bestätigt deinen Beitritt." with Cancel,
  and the household appears when approved (realtime or refresh on resume). Admins see a count on
  the household page and the requests with Approve/Decline.
- Old store builds: `accept_invite` old signatures answer `requested` as an unknown status; they
  show their generic error. Accepted: approval is new and opt-in.
