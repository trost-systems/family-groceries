# Analytics and error tracking

After the first sign-in on a device, before onboarding or the list, the app asks once whether it may store a random install id on the device and send pseudonymous usage data and error reports to PostHog (EU); the text names Peter Trost as the one asking and links the privacy policy. Both answers are one tap. With a yes it sends `first_open`, then one event per add, tick, household created, invite accepted and category or store reorder, never an item name or other list text; with a no it sends nothing, ever. Mehr → Nutzungsdaten switches it on or off for the device; off stops sending at once and deletes the install id. The install id exists only after a yes. A long press on the version line marks the device internal (its data is filtered out of the gate insights) and shows "Testfehler senden". Edge functions report their exceptions, tagged with the function name. Background and definitions: `docs/ANALYTICS.md`.

## Sub-features

- `an-consent` the consent screen (`analytics-consent`, buttons `analytics-consent-decline` "Ablehnen" and `analytics-consent-accept` "Einverstanden", no draft mark (Peter approved the wording on 2026-10-30), title "Darf Hummlist Nutzungsdaten erfassen?", the link "Datenschutzerklärung" (`analytics-consent-privacy`) to https://hummlist.com/datenschutz) right after the first sign-in on a device, route `/analytics-consent`; an invite link keeps its code through it; an MCP authorization tab is not interrupted.
- `an-decline` after "Ablehnen" nothing reaches the PostHog host, also after adding and ticking.
- `an-events` after "Einverstanden": exactly one `first_open` per device, then `household_created` / `invite_accepted` (method `link` or `code`), `item_added` (source `typed`, `spoken`, `suggestion`), `item_ticked` once per tick (undo sends nothing: a put-back from "Zuletzt verwendet" within 10 minutes of the tick is no `item_added`), `category_reordered` (scope `default` or `store`), `store_reordered`; each with `household_id`, none with list text.
- `an-switch` Mehr → Nutzungsdaten (`more-analytics`, "Nutzungsdaten und Fehlerberichte senden") shows the decision and changes it; off stops sending at once.
- `an-install-id` the install id (`analytics.install_id` in the device cache; `analytics.install_id` in the web's localStorage too) is absent before the answer and after a no, made at the yes, deleted when switched off, and new after switching on again. An id an older build stored without a yes is deleted at the next start. Proved in `e2e/tests/analytics.spec.ts` (localStorage) and `app/test/analytics/analytics_test.dart`.
- `an-internal` a long press on `more-version` toggles "Interne Installation" (`more-internal`) and the "Testfehler senden" button (`more-test-error`).
- `an-errors` an uncaught app error and an edge-function exception arrive in PostHog error tracking, scrubbed.
- `an-sdk` (job 44) the app runs posthog_flutter (posthog-js on the web) only after the yes: before it no request reaches the PostHog host and posthog-js is not even fetched; off closes the SDK and deletes its files (ids, queue). Only allow-listed keys leave a browser.
- `an-flags` (job 44) `Analytics.flags.isOn(key)`: off before the yes, after a no and in builds without a key; what `/flags` served after the yes. No UI uses a flag yet, so it is proved in `app/test/analytics/flags_test.dart` and by the `/flags` request in the collector log.

## How to get to it (user POV)

- Sign in on a new device (or a fresh browser profile): the question comes before "Haushalt anlegen" or the list.
- Mehr → Nutzungsdaten.
- Mehr → hold the version line at the bottom.

## Driving it with fg

Preconditions:

- `fg` builds have no PostHog key by default, so analytics is off there: no consent screen, no Nutzungsdaten section, nothing sent. `fg login` goes straight to the list as before. The web e2e build (`app/config/e2e.json`) has a stand-in key and host `https://posthog.invalid`, which the spec answers with a fake collector.
- With `FG_POSTHOG_HOST=http://127.0.0.1:<port>` (job 44) `fg up` builds the app with a stand-in key and that host, which must be on this machine. Start the collector first: `deno run --allow-net=127.0.0.1 --allow-write cli/posthog_collector.ts <port> <out.jsonl> [flag=true ...]`. Every request lands in `<out.jsonl>` (gzip decoded); `/flags` answers the flags given. `fg login` then stops on the consent screen (it times out waiting for the list: tap `analytics-consent-accept` or `-decline`). `fg up` clears the app's data, so the consent is asked again after each `fg up`.

- **`an-sdk`, `an-events`, `an-errors`, native (Linux).** `FG_POSTHOG_HOST` as above, collector running. Login screen and consent screen: `<out.jsonl>` stays empty. Accept, add an item at once (`fg type --input Hafermilch --key add-item-field --submit`, then `fg tap --text Schließen`; `fg back` there closes the Linux window), tick it: one `POST /flags/` at the yes, then about 30 s later one `POST /batch/` with `first_open`, `item_added`, `item_categorized`, `item_ticked`, each with our context (`install_id`, `household_id`, `platform: linux`, `is_internal: true`) next to the SDK's `$app_*`, `$os_*`, `$screen_*`, `$session_id`. An uncaught error (a failed `fg marionette -- scroll-to` raises one in the debug harness) arrives as `$exception` with a scrubbed value such as `Bad state: <w> not <w> after <n> <w>`. Switch `more-analytics` off, add and tick again, wait 45 s: no new line, and the SDK's folder `~/.local/share/com.hummlist.app/posthog/phc_fg_local_collector` is gone. Job 44's run: `docs/screenshots/44/native-linux-collector.txt`.
- **`an-consent`, `an-decline`, `an-events`, `an-switch`, web.** Run `scripts/ci-e2e.sh --spec tests/analytics.spec.ts` (GitHub Actions; with Docker also `scripts/gates/e2e.sh --workers=1 tests/analytics.spec.ts`, which takes `/tmp/fg-e2e.lock` itself; never wrap it in `flock`). Six tests pass, the last one the app half of `an-internal`/`an-errors` against the fake collector (below). With `--download <dir>`, `screenshots/` holds `analytics-01-consent-after-sign-in.png` (the question after sign-up), `analytics-02-declined-then-welcome.png`, `analytics-03-collector-declined.png` (the collector log: 0 requests), `analytics-04/05-more-switch-on/off.png`, `analytics-06-collector-accepted.png` (one line per event: `first_open`, `household_created`, `item_added` ×3, `item_ticked` ×3, nothing after the switch went off), `analytics-07-consent-before-list.png` and `analytics-08-declined-then-list.png` (an existing member on a new device), and `analytics-07-consent-en.png` and `analytics-08-more-switch-en.png` (the English texts).
- **`an-internal`, `an-errors` (app).** In CI the spec's test "an internal device sends a test error, scrubbed, to error tracking" covers it against the fake collector. The proof against the real PostHog project 319492 is manual, never from CI. Build: `cd app && flutter build web --release --source-maps -o /tmp/proof --dart-define=SUPABASE_URL=https://fake-supabase.invalid --dart-define=SUPABASE_PUBLISHABLE_KEY=sb_publishable_fakeproof --dart-define=POSTHOG_PROJECT_API_KEY="$POSTHOG_PROJECT_API_KEY" --dart-define=POSTHOG_HOST="$POSTHOG_HOST"` with `~/groceries-ops/env` sourced. Optional readable frames: `POSTHOG_CLI_API_KEY=$POSTHOG_PERSONAL_API_KEY POSTHOG_CLI_PROJECT_ID=$POSTHOG_PROJECT_ID npx @posthog/cli@0.19.0 --host https://eu.posthog.com sourcemap process --directory /tmp/proof --delete-after`. Serve with `node e2e/serve.mjs /tmp/proof 5<prefix>80 &`, then `flock /tmp/fg-e2e.lock node e2e/analytics-proof.mjs http://127.0.0.1:5<prefix>80 <out>`. It prints `before consent: 0` and, since job 44 (posthog-js), a `POST https://eu.i.posthog.com/flags/` and `POST https://eu.i.posthog.com/e/` answered 200 (`first_open`, then `$exception`); served without the production CSP it also loads the remote config from `eu-assets.i.posthog.com`, which the deployed app's CSP blocks; `<out>/ac11-02-internal-install.png` shows "Diese Installation zählt jetzt als intern."; `<out>/ac11-sent.json` has the `$exception` with type `StateError`, value "Bad state: <w> error (<w>, <w>)" (job 33a: every word outside the runtime's error templates is reduced to `<w>`), `is_internal: true` and frames with a `chunk_id`. The issue list: `curl -H "Authorization: Bearer $POSTHOG_PERSONAL_API_KEY" https://eu.posthog.com/api/environments/319492/error_tracking/issues/` names a `StateError` issue with that description.
- **`an-errors` (edge functions).** `deno run --config supabase/functions/deno.json --allow-env --allow-net analytics/proofs/edge_exception.ts` with the env sourced. It prints two batches answered 200: an `Error` with value `23505` (the caught database failure; its message is not sent) and a `TypeError` "Job 19 forced test exception (edge function voice)", both with `function_name: voice`, `is_internal: true`, and no "Hafermilch", token or header anywhere. The issue list above shows both.

## Gotchas

- The consent decision belongs to the device (browser profile), not the account: a second sign-in in the same Playwright context is not asked again, a new context is. Specs answer it through `signUp` or `answerConsent`.
- posthog-js sends every 3 s, the native and Linux SDKs every 30 s (or at 20 events); "nothing was sent" needs a wait past that (the spec waits 7 s on the web, the Linux recipe 45 s).
- posthog-js drops events from user agents that look like bots unless `opt_out_useragent_filter` is set (the app sets it): a headless browser otherwise sends nothing after the yes.
- On `/analytics-consent` the MCP consent page's "Ablehnen" is not on screen; the two never show together.
- Chromium runs the wasm build (job 28): its error frames name Dart functions without lines. The source-map proof above needs the JS build, which is what `--source-maps` and Safari use.
- Never send proof events without `is_internal` (the proofs set it through the `fg.test` user, the internal device mark and `ANALYTICS_INTERNAL=true`).
